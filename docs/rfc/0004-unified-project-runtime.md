## The ask

- **Recommendation (BLUF):** make Agentic Inquiry the single runtime an AFP pack installs into a project, in all four harnesses, by removing the write paths that cannot be governed or have never produced data, and adding one governed context face. Read the brain through `brain_search`, `brain_get` and `brain_neighbors` and cite it by id; never copy or index it.
- **Why now (SCQA):** RFC-0003 accepted a knowledge architecture in which this runtime indexes the brain into a library store and federates results. Between 28 September and 3 October 2026 the runtime failed in the one workspace that used it: `ai mcp` read a different, empty store from the one `ai index` wrote; the CLI ranked archived and deleted files first; the AFP engine's hook bridge flagged every write outside the repository as blocked; and the lifecycle ledger filled with 111 refresh rows nothing consumed, while its capture path, the reason the hooks exist, held no production row at all. The brain now has its own MCP server. A knowledge layer beside a code layer would mean two servers, two packs and two hook sets to keep honest in four harnesses, so project context and code intelligence must be one runtime that behaves the same in Claude Code, Codex, Cursor and Pi. The question is what this runtime must become for that to hold.

## Problem & goals

The runtime indexes code and documents well and governs nothing. Measured on 3 October 2026 (details under Evidence): `ai mcp` from an unregistered folder exits with "the following arguments are required: --project-id", although shipped AC29 says the configuration default applies; `ai index` resolves its store through the environment resolver and `ai mcp` through the binding, which is why one wrote 113,197 chunks and the other read none; `ai index` never removes rows for deleted files (565 of 593 indexed files were gone after the brain's folder flatten on 2 October); `session_manager.py` maps any statistics error to `index_health: empty` and `index_state.py` maps a count error to READY. Memory saves are active the moment they land, carry `content_source: user_input` whatever their origin, and link to no file. The pack's five hooks run through the AFP engine's `plugin_hooks.py`, which confines paths to the git root and answers `decision: block` on any Write elsewhere. The capture path those hooks exist for has never received an observation from a harness.

Meanwhile the brain is Markdown with claims, licence flags and verification dates behind its own server, and the initiative folders hold confirmed engagement facts in handoff files that no tool reads with provenance.

**Goals.**

- One pack, one runtime, the same behaviour in Claude Code, Codex, Cursor and Pi: MCP tools are a feature Claude Code, Codex and Cursor all support and Pi reaches through the `pi-mcp-adapter` extension; Pi has no MCP in core and Codex projects no commands, so every capability is a tool with a CLI verb behind it, and no capability depends on a hook.
- Every durable project fact is a Markdown page with sources, a status, a licence flag and a named confirmer; no MCP tool can make it accepted; an acceptance with no CLI record, or a page changed after acceptance, is reported by `check`.
- Code intelligence stays: tree-sitter entities and relationships (Apex included), Salesforce metadata, impact and lineage, cited document search.
- The brain is read live and cited by id; a citation carries the claim's `verified` date and `licensed` flag, `check` verifies both against the brain's claim records, and a licensed citation fails `check` in a `render` project.
- One root, one index store, one context folder: every entry point resolves them through one function; a nested repository or context root is excluded from its parent's index; a project session never reads another project's store.
- Every index is derived and rebuildable; a second `ai index` leaves no row for a file that is gone.

**Non-goals.**

- A team or hosted provider. RFC-0003 D7 stands; git is the share.
- Fusing project hits and brain hits into one ranked list. Two bounded, cited lists are what a reader can check; fusion across stores of different size buries the small one.
- Replacing core `project-knowledge`. It keeps `docs/knowledge/` JSONL for gate-written engineering residue; the writers and readers differ.
- A generative model in the write path or the query path.
- Proving that a human typed `/ctx accept`. No harness exposes that proof; the design bounds the claim instead.
- Keeping capture alive on the hope that a harness will one day send observations. If one does, that is a new RFC with a producer named.

## Proposal

Vocabulary for this RFC: the **root** is the folder a session binds to; the **context folder** is `<root>/docs/context/`; the **index store** is the LanceDB and SQLite directory that holds the root's derived index; the **ledger** is `INQUIRY_HOME/projects/<identity>/records.sqlite3`.

**Keep.** Parsers (`parsers/implementations/unified_code.py` with its query files including `apex.scm`, `salesforce_metadata.py`, `document.py` on `unstructured` with its `docx`, `md`, `pptx` and `xlsx` extras and on `pdftext` for PDF, with `.rtf`, `.odt`, `.odp`, `.ods`, `.epub` and `.rst` leaving `SUPPORTED_EXTENSIONS` because their partitioners need a pandoc binary), the indexing pipeline, the storage facade over LanceDB and SQLite, hybrid search, impact and lineage, the MCP server (`ai mcp`; `ai serve` and the leading-flag route become aliases that reach the same entry in `mcp/cli.py`, and `ai serve --port` keeps the loopback-only HTTP transport), the loopback rule of `bind_host` moved to `mcp/bind.py` with its API-key branch retired, the CLI, the lifecycle contract's capability report, hook envelope, binding registry and `purge`, the standalone plugin's skills and commands except `memory`, the AFP pack, Gemini support through `gemini-extension.json` repointed from the daemon to `ai mcp --root ${workspacePath}`, because the extension's `cwd` is `${extensionPath}`.

**Remove.** Every durable write path without a person in it and every path that never produced data:

- Memory: the MCP tools `save_memory`, `recall_memories` and `add_knowledge` with `content_type="text"`; the CLI `ai memory save | recall | list`; the `memory/` package and its tables; the consolidation loop; the prompt text recommending `save_memory` in `mcp/tools/context.py`, `mcp/tools/info.py`, `mcp/tools/search.py` and `mcp/services/context_builder.py`; the standalone plugin's `skills/memory/`, the memory call in `skills/onboard/`, and `servers/daemon/managers/memory.py` with the daemon it belongs to; in the pack, the `memory` command, skill and Pi alias, the `ai memory save` lines in `skills/onboard/SKILL.md` and `commands/onboard.md`, the `/ai:memory` line in `skills/help/SKILL.md`, the `inquiry-librarian` agent's memory role, the capture text in `skills/ai/references/integration.md`, the hook's "no capture success is claimed" fallback, the `pack.toml` description phrase "preserve project knowledge across sessions", and every other memory and capture reference in the pack, enumerated by the `subtraction` spec; the known set is `.apm/skills/ai-enquire/SKILL.md`, `.apm/agents/inquiry-explorer.md`, `.apm/agents/inquiry-guide.md`, `.apm/skills/ai/references/knowledge.md`, both `evals/eval_queries.json` files and the `plugin.json` description.
- Lifecycle capture and refresh: observations, artifacts, receipts, `pending`, `reconcile`, the UserPromptSubmit evidence stage and the SessionStart recall of capture rows. The ledger keeps bindings and notification rows; `purge` keeps erasing event rows and tombstones and drops its memory sweep.
- REST (D8): `server/` except `bind_host`, `ai server start | stop | status | restart`, `cli/client.py` with the bare `ai` and `ai shell` clients (a bare `ai` prints help), `scripts/entrypoint.py`, the `Dockerfile`, `docs/mcp/deployment.md`, the standalone plugin's daemon (`extensions/claude/ai/servers/`), `scripts/socket_client.py` and `config/daemon-defaults.yaml`, the Gemini extension's `servers/daemon/`, `scripts/socket_client.py`, `commands/ai/memory.toml`, `hooks/hooks.json` (whose scripts import `server.http_client` and `server.lifecycle`) and `ai-dev/commands/ai-dev/server.toml`, the standalone plugin's `ai-dev/skills/server/SKILL.md`, and the `fastapi`, `uvicorn`, `slowapi` and `python-multipart` dependencies.
- Hooks: the standalone plugin's hook scripts (`extensions/claude/ai/hooks/`); the pack's PostToolUse, UserPromptSubmit, PreCompact and Stop hook bodies.
- RFC-0003's library environment, federated search and facade `audience` filter for this runtime.
- The torch path as a required dependency (D7).

**Add: the context face.** A package `agentic_inquiry/context/` that imports the standard library only and spawns no subprocess (git facts are read from `.git`, `.git/config` and the `gitdir:` line of a `.git` file directly), so AC3 and AC26 keep their meaning. Its Principle 4 exception, added to the charter by this RFC, is the ledger's: synchronous file I/O and the lock file in `context/`, reached from async callers through `asyncio.to_thread`. The resolution function lives in `agentic_inquiry/integration/resolve.py`, because `integration/` is already held to the lazy-import rule of AC3, while `storage/__init__.py` imports the facade eagerly:

- `pages.py`: a strict parser for the YAML subset the brain's pages use (string scalars, ISO dates, the booleans `true` and `false`, an empty value after a colon read as null, block lists, inline lists of scalars, one level of inline mapping for `sources`), page validation, deterministic `index.md` and `index.jsonl`, both derived and git-ignored (`init` writes `docs/context/.gitignore`), rebuilt by any reader when older than any page or `README.md`, and excluded from `ai index`; both written under one lock file keyed on the canonical root at `INQUIRY_HOME/locks/<sha256(root)[:16]>`, not in the index store, so concurrent `propose` and `accept` never interleave. `check` normalises the brain's string-typed `"licensed": "false"` to a boolean before comparing.
- `store.py`: the context folder's propose, accept, reject, supersede and the acceptance log, over the root that `integration/resolve.py` returns.
- `graph.py`: an accepted page, and only an accepted page, becomes a graph entity by `kind` (`decision` to `DECISION`, `requirement` to `REQUIREMENT`, `fact` to `CONCEPT`; all three exist in `models/graph_entity.py` and nothing produces them today) with `documents` edges to the files it cites and `governs` edges to the code entities it cites; `GOVERNS` and `GOVERNED_BY` are added to `models/graph_relationship.py` with their inverse and metadata map entries; `supersedes` maps to the existing `REPLACES`.

**One resolution function** (`integration/resolve.py`), used by `ai index`, `ai search`, `ai status`, `ai integration status`, `ai mcp` through `mcp/cli.py`, the `/ai:*` skills and the context face:

1. The root is an explicit `--root <path>` when given; otherwise the git toplevel when the working folder is inside a work tree; otherwise the nearest ancestor below `$HOME` that holds a context folder or `.agentic-inquiry/project.toml`; otherwise the folder itself. The walk never selects `$HOME`, `INQUIRY_HOME` or `/`, because `~/.agentic-inquiry/` is the ledger home and not a project marker. The Cursor projection passes `--root ${workspaceFolder}`, because Cursor starts stdio servers in the home folder, not the workspace (spiked 3 October); Claude Code, Codex and Pi start them in the project folder, so their projections pass no root; the Gemini extension starts them in `${extensionPath}`, so `gemini-extension.json` passes `--root ${workspacePath}`. `ai context init` and `ai integration enable` refuse an explicit root that lies inside a work tree below its git toplevel, naming the toplevel, so neither a context folder nor an identity file sits in a subtree that step 3 excludes from its parent root.
2. The index store and namespace, in precedence: an explicit `--project` or `--config` flag, which the output names as an override; the root's binding, when `ai integration enable` created one, which outranks `INQUIRY_CONFIG` and `INQUIRY_ENV` so that a terminal `ai index` and a GUI-launched `ai mcp` with different environments read one store; for an unbound root, `INQUIRY_CONFIG` or `INQUIRY_ENV`; the root's project-local environment under `<root>/.agentic-inquiry/`; otherwise the derived store `INQUIRY_HOME/stores/<ns>/` with `ns` the first 16 hex characters of the SHA-256 of the canonical root path, a path family separate from the ledger's `INQUIRY_HOME/projects/<identity>/`. `enable` ignores the two variables and binds a project-local environment when one exists, otherwise the derived store, which it creates when absent; it writes `<root>/.agentic-inquiry/project.toml` when absent in both cases, so enabling never splits a store, never binds a shared global store, and the identity file step 1 reads exists for every enabled root. Every binding of one identity names one store: `enable` for a further client reuses the store the first binding recorded; `ai index`, `ai search` and `ai status`, which have no client, read it from any binding of the identity; `ai setup local` on a bound root prints that the root is bound and that the new environment is used only after `disable`, `purge`, `enable`.
3. Nested roots are excluded: `ai index`, the code face and the context face skip every folder below the root that is itself a git toplevel, holds a context folder or holds `.agentic-inquiry/project.toml`, the same markers step 1 reads, so `~/work/agentic-enterprise` indexes its own files and not `rde-certification/`, and `~/work` or `~/projects/Accounts` indexes nothing but its own loose files.
4. Refusals: the context face refuses the root `$HOME` or `/`, refuses any root under `INQUIRY_BRAIN_ROOT` for writes, refuses `ai index` of that tree and of any tree that contains `wiki/graph/claims.jsonl` (so the brain stays unindexed when `INQUIRY_BRAIN_ROOT` is unset), and `context_propose` refuses until a person has run `ai context init` in the root. The context folder and every page are resolved before use and must stay inside the root; a symbolic link as the context folder, as a page or as an `_archive/` entry is refused on read and on write, so no page reaches `brain/` or leaves the root through a link. `ai mcp` changes its working directory to the resolved root after resolution, so the tools that confine paths to `os.getcwd()` today (`mcp/tools/knowledge.py`, `mcp/tools/direct_access.py`, `mcp/tools/search.py`, `indexing/pipeline.py`) confine to the root on Cursor too, and the `subtraction` spec replaces those reads with the resolved root. The code face's read tools serve wherever they are started; its write tools, `index_files` and `add_knowledge` with `content_type` `file` or `directory`, write only the root's own index store and refuse the roots `$HOME` and `/`.
5. A folder that moves (a pursuit promoted into `delivery/`) gets a new derived namespace and an empty store; the next `ai index` rebuilds it, because every index is derived. The move itself is `ai integration disable` and `ai integration purge` before the move, then `enable` in the new place, because the binding stores the canonical root and the identity in `project.toml` travels with the folder. Without that sequence a hook returns `project_identity_invalid` for a root that differs from the bound one (AC13) and `disable` and `purge` refuse for the same reason (AC12). `enable` in the new place succeeds because AC11, as amended, refuses an id bound to a different canonical root only while a binding of it is enabled or an event row remains; after `disable` and `purge` neither holds, and `enable` rewrites the bindings' root. The acceptance log is keyed on the identity, so accepted pages keep their log matches across the move.

This amends shipped AC29 and the Vocabulary entries for storage namespace and ledger home, and makes initiative folders roots with a context folder once the folder contract admits `docs/context/` and `.agentic-inquiry/` (precondition under Migration).

**Page schema** (file name equals `id` for pages; `README.md` and `index.md` are not pages; `id` and every `supersedes` value match `^ctx-[0-9]{8}-[a-z0-9-]{1,60}$`; a slug collision on one day gets a `-2` suffix):

```yaml
---
type: Context
kind: fact
id: ctx-20261003-example-fact
title: The example fact this page records
status: accepted
licensed: false
sources:
- {path: handoff.md#facts, date: 2026-09-30}
- {claim: C-EXAMPLE-001, verified: 2026-09-24, licensed: false, date: 2026-09-30}
tags: [example]
created: 2026-10-03
valid_from: 2026-09-30
valid_to: 2026-11-30
confirmed_by: Sammy Basha
confirmed_on: 2026-10-03
accepted_via: command
supersedes: [ctx-20260928-example-earlier]
superseded_by:
superseded_on:
promote: false
---
```

`kind` is `decision`, `requirement` or `fact`. `sources` entries are `{path, date}` inside the root (the `#anchor` is stripped before the confinement check), `{url, date}`, `{brain: <node id>, verified, licensed, date}`, `{claim: <claim id>, verified, licensed, date}` or `{entity: <code entity>, path, date}`. `licensed` on the page is true when any cited brain source is licensed or when the author sets it. `status` is one of three values. `accepted_via` is `command` (through `/ctx`), `cli` (run through the CLI directly) or `edit` (frontmatter edited by hand, no log entry); the value is asserted by the caller (`/ctx` passes `--via command`), not observed. `confirmed_by` and `confirmed_on` are required when the status is not `proposed`. `valid_from` and `valid_to` are world time; `created`, `confirmed_on` and `superseded_on` are record time. `supersedes` is a list so two pages can merge into one; accepting a page sets `status: superseded`, `superseded_by` and `superseded_on` on each page it names and never deletes. The body is capped at 8 KiB and its first paragraph is the statement. `docs/context/README.md` carries `audience: render` or `builder`; when the file is missing or invalid the audience is `render`. `promote: true` is a request: `ai context list --promote` prints the page and its sources as text the person pastes into a brain session, where the brain curator compiles it; nothing in a project session writes into `brain/`, and no brain session reads engagement folders.

`type: Context` is a project-tier type, not a brain type. A page lifts into the brain by the curator reading it, not by conversion: the frontmatter dialect is shared, the schema is not. The `context-face` spec carries by name: the quoting rule for flow scalars containing `: , # { }`; a `supersedes` value naming a missing, proposed or already superseded id, or forming a cycle; `accept` on an accepted page; a same-day slug collision across branches.

**MCP tools** in `mcp/tools/context_pages.py` (the existing `mcp/tools/context.py` holds `build_context` and keeps its name): `context_search(query, status=accepted, as_of=today, limit)` returning the root, counts and hits with their provenance fields, excluding pages whose `valid_to` has passed unless `as_of` says otherwise; `context_get(id)`; `context_propose(kind, title, body, sources, tags, valid_from, supersedes)`, which hard-codes `status: proposed`, generates the file name, and returns the page id, the page text and the review commands with the id filled in. `initialize.instructions` states the counts, the audience and the rule that proposals are not facts. The storage facade filters every `docs/context/` chunk on the context folder's live status at query time, so `search_knowledge`, `build_context`, `fetch_content`, `find_similar`, `search_code`, `graph_traverse`, `understand_entity` and `analyze_impact` all see accepted pages only, `_archive/` is never indexed, and an acceptance is visible without a re-index. The filter applies on every query path, not only the facade's search methods: the direct `advanced_filter` calls on `db_manager` in `mcp/tools/direct_access.py` and `mcp/tools/search.py` are routed through the facade or filtered in place, row by row in the `subtraction` spec.

**CLI** `ai context init | propose | accept <id> | reject <id> | list | reindex | check | eval`. `init` creates the context folder, its `README.md` and its `.gitignore`, writes `<root>/.agentic-inquiry/project.toml` when absent with the grammar `enable` uses so that every context root has an identity, logs the audience in the acceptance log, and is the person's act that admits writes. `accept <id>` prints the page and the ids it supersedes, takes `confirmed_by` from `user.name` in a work tree, reading `.git/config`, then `~/.gitconfig`, then `$XDG_CONFIG_HOME/git/config`, without following `include` or `includeIf` directives, and from the OS user otherwise, flips the status, writes `confirmed_on` and `accepted_via`, supersedes the named pages, regenerates `index.md` and `index.jsonl`, and appends one line to `INQUIRY_HOME/context-acceptances.log` with the project identity, the canonical root as data, the page id, the SHA-256 of the canonical frontmatter plus body, the OS user and the time; `check` matches a log entry on identity plus id, so a moved folder keeps its matches. `reject <id>` moves the page to `docs/context/_archive/<date>/`. `reindex` regenerates `index.md` and `index.jsonl` and asks the index store to re-read the context folder; it does not run `ai index`. `check` exits 1 on any schema violation, on a `path` source outside the root, on a `licensed: true` page under `render`, on a page whose `licensed` is false while any cited source is licensed, on an unknown `brain` or `claim` id, on a `licensed` value that differs from the brain's record, and on an accepted page whose acceptance-log entry exists but whose hash no longer matches; it prints the audience in force and warns, without failing, on `verified` drift (the brain re-verified the claim since citation), on `README.md` changed after `init`, and on an accepted page with no log entry on this machine, so a clone or a second machine passes with warnings that tell the reviewer what to look at. The brain is reached through `INQUIRY_BRAIN_ROOT` (configuration, never a literal path): claims against `wiki/graph/claims.jsonl`, nodes against `wiki/graph/mcp/nodes.json`; a `render` page whose body contains the statement of any licensed claim fails; when the brain is unreachable `check` reports the skip. `eval <cases.yaml> [--config <harness mcp file>] [--expect-empty]` runs known-answer cases in-process or through the server a harness config names.

**What D3 guarantees and what remains possible, per harness.** Guaranteed everywhere: no MCP tool accepts; an accepted page with no log entry, or with a hash that no longer matches its frontmatter and body, is reported by `check`. Claude Code: `/ctx accept <id>` runs `ai context accept` through the command's `!` pre-execution, and `ctx.md` carries `disable-model-invocation: true`, so the model cannot invoke the command; the model can still run the CLI through its shell tool. Cursor and Pi: the projected command's Bash call is executed by the model, so the acceptance is model-run on the person's instruction. Codex: no commands project; the skill acts on a message that is exactly `accept <id>` or `reject <id>` after a proposal it just presented, and that too is model-run. In all four, the skill forbids running `ai context accept` without that instruction, the log records every CLI acceptance and none made by `edit`, `accepted_via` is asserted by the caller and not observed, the model can append a forged log line with a computed hash through its shell or Write tool, and `confirmed_by` is configuration-derived, not proven. `init` is a CLI verb the model can run the same way. The audience file is a residual too: a model Write can set `audience: builder` in `docs/context/README.md`; `init` logs the audience, and `check` prints the audience in force and warns when the file changed after `init`. These are stated so that no reader takes the log as proof.

## Options considered

Two decisions, two axes.

**Axis 1: where governed project context sits relative to code intelligence and the brain.** The options exhaust the axis: nothing changes; no server at all; the brain's server serves project context too; a separate project server beside the code runtime; the code runtime serves both.

| Option | Description | Prior art | Trade-off against the goals |
| --- | --- | --- | --- |
| A. Do nothing | RFC-0003 as accepted: fix the defects, build the library index and federation | RFC-0003 | Indexes the brain, which D4 rules out; memory stays ungoverned until the D6 promotion ladder is built; the defects are fixed on the same surface that produced them |
| B. Files only, no server | Markdown pages read with the harness's file tools, a skill teaches the convention | Cline Memory Bank, Karpathy's llm-wiki | No search, no provenance check, no confinement; each harness re-implements the rule in prose |
| C. The brain server serves project context | One TypeScript server reading `wiki/` and a project's `docs/context/` | Basic Memory's single-server shape | Puts a shared read-only server in the write path of every client folder; its cwd is the brain, not the project, so confinement is by argument, not by construction |
| D. Separate project server beside the code runtime | A small context server and pack beside Agentic Inquiry | Context Portal, Basic Memory | Two servers, two packs, two hook surfaces in four harnesses; the join between a decision and the code it governs crosses a process boundary |
| E. The code runtime serves both (recommended) | This RFC | The brain's own pattern: Markdown authority, derived indexes, a curator gate; Graphiti's temporal fields | Keeps a large base; mitigated by subtraction first and the validation below as the gate |

**Axis 2: how the runtime reaches that shape.** The options exhaust the axis: adopt an external store; add the context face and change nothing else; subtract and add; rewrite.

| Option | Description | Prior art | Trade-off |
| --- | --- | --- | --- |
| F. ## Risks & what would make this wrong

- **Pre-mortem.** The model runs `ai context accept` itself or forges a log line: the residuals are stated per harness under D3, `disable-model-invocation` closes the command path in Claude Code, and the person reviews `git log -p docs/context/` with `check`'s warnings. Subtraction breaks a consumer: the removals and the criteria table are listed here, the `subtraction` spec carries the erratum text, and the pack test asserts the surviving surface. A parent folder becomes a store: nested roots are excluded from indexing, `context_propose` refuses until `init`, and `eval --expect-empty` from a client repository is a standing check. A licensed claim is pasted into a page body without a citation: `check` matches bodies against licensed claim statements when the brain is reachable; the match catches verbatim text only, a paraphrase passes, and when the brain is unreachable the check is skipped and reported. The brain is unreachable: `check` skips id verification and says so; search still works. The dependency diet misses its gate: the numbers live in the `index-lifecycle` spec with their derivation, and the fallback is a lazily loaded embedder behind the first vector query. A harness starts the MCP server with a cwd other than the project folder: Cursor does (spiked 3 October), so the resolution function takes `--root` first and the Cursor projection passes `${workspaceFolder}`; a harness that offers neither a project cwd nor a workspace variable has no supported projection.
- **Key assumptions.** The base can be subtracted to a trustworthy runtime rather than rewritten; the spike below shows ranking is sound and the defects are in lifecycle, binding and health reporting, and the validation gates every session after this. Claude Code and Codex start a stdio MCP server in the project folder (run, 3 October, under Evidence); Pi through `pi-mcp-adapter` spawns with `process.cwd()` (read, not run); Cursor resolves `${workspaceFolder}` to the folder holding `.cursor/mcp.json` (its documentation, read, not run: the project run needs the approver to enable the project server once in Cursor's MCP settings, with the probe at [`0004-notes/mcp-cwd-probe.py`](0004-notes/mcp-cwd-probe.py)); so one root per session holds with `--root` on Cursor only. Open question 2 records `roots/list` as the alternative. Context pages number in the tens to hundreds per folder, so an in-memory index rebuilt from file stats is enough. The AFP engine keeps wiring a SessionStart bridge for any plugin-runtime pack and keeps refusing every plugin-runtime hook without `user-scope-hooks` (read in `plugin_runtime.py` and the pack's `pack.toml` comment on 3 October). `unstructured` with the `docx`, `md` and `pptx` extras partitions DOCX, Markdown and PPTX, and `pdftext` extracts PDF text, without the `[all-docs]` extra (spiked 3 October); the `xlsx` extra partitions XLSX through `openpyxl` (read, not spiked); image and OCR partitioning of PDFs, which `[all-docs]` provided through `unstructured-inference`, is lost outside the `torch` extra, and `.doc` keeps its LibreOffice dependency at run time.
- **Drawbacks.** The REST surface, the Gemini daemon and the interactive `ai shell` client disappear, so a non-MCP integration has no entry point until someone needs one. `/ai:memory` goes away, and with it RFC-0002's capture design, which never ran. Two servers per session remain, brain and project; this RFC makes them one product boundary, not one process. Re-embedding on upgrade costs one indexing pass per environment. RTF, ODT, ODP, ODS, EPUB and reStructuredText documents are no longer parsed, because their `unstructured` partitioners need a pandoc binary outside the Python install. Pi reaches the MCP server only through a third-party extension, Codex only after a person trusts the folder in the user config, and Cursor only after a person enables the project server once; each is a one-time step the pack README must carry, and none can be removed by this runtime. The SessionStart identity line the engine injects ("Skill workflow receipt") is engine behaviour this RFC cannot remove; the pack only stops triggering it on the other events.

The rule that every capability is a tool with a CLI verb rests on Pi, which has no MCP in core, and on Codex, which projects no commands, not on any client's capability list. [Codex CLI memories](https://codex.danielvaughan.com/2026/05/01/codex-cli-memories-persistent-context-session-memory-ecosystem/): global, background-extracted, no approval step. No external project was found that combines a proposed-to-accepted gate with provenance on Markdown over MCP; that gap is why the context face is built rather than adopted.
